# 수집 설정 UX 결정

## 배경

기존 주제 등록 화면은 사용자가 `1회 수집 건수`와 `수집 주기(분)`를 직접 입력하게 했다.
그러나 사용자는 외부 검색 소스에 기사가 몇 건 존재하는지 미리 알 수 없고, 실제 저장 건수도
검색 결과 수, 키워드 필터, URL 중복 제거에 따라 달라진다. 따라서 기사 건수를 사용자에게 묻는
방식은 결과를 예측하거나 제어하기 어렵다.

## 결정

- 사용자는 기사 수가 아니라 새 기사를 확인할 주기를 결정한다.
- 일반 설정 화면에서 `1회 수집 건수` 입력과 표시를 제거한다.
- 검색 API 호출량을 보호하는 `batchSize`는 제품 내부 제한으로 유지한다.
- 주제 등록 요청에서는 `batchSize`를 생략하여 백엔드 기본값 10을 사용한다.
- 자유 숫자 입력이던 `수집 주기(분)`을 다음 선택지로 바꾼다.
  - 1시간마다
  - 6시간마다
  - 12시간마다
  - 매일 한 번 (기본값·권장)
- API의 `intervalMinutes` 형식은 유지하며 각 선택지를 각각 `60`, `360`, `720`, `1440`으로 보낸다.
- 기존 데이터의 임의 주기 값은 조합 목록에서 `N분마다`, `N시간마다`, `N일마다` 형태로 표시한다.

## 사용자에게 보이는 동작

사용자는 주제를 만들 때 `매일 한 번`과 같은 주기만 고른다. 시스템은 실행 시 검색 소스의 최신
기사를 확인하고 키워드 필터와 중복 제거를 거쳐 새 기사만 저장한다. 화면에서 없앤 수집 건수는
"새 기사 N건을 보장하는 값"이 아니라 외부 검색 API에 한 번 요청할 최대 결과 수이며, 사용자가
직접 결정하지 않는다.

현재 자동 반복 수집은 구현 전이므로 선택한 주기는 설정값으로 저장만 된다. 자동 스케줄러가
도입되기 전까지 실제 수집은 `지금 실행`으로 시작한다.

## API 및 호환성

Notion의 `수집 주제 등록` 명세에서 `batchSize`와 `intervalMinutes`는 선택 필드다. 이번 변경은
요청·응답 형식을 변경하지 않는다. `batchSize`를 생략하면 명세와 백엔드의 기본값 10이 적용되고,
`intervalMinutes`는 기존 정수 분 단위로 전송한다. 조합 조회 응답의 `batchSize`도 호환성을 위해
유지하되 일반 화면에서는 표시하지 않는다.

## 향후 자동 수집 정책

자동 스케줄러를 구현할 때는 마지막 성공 수집 이후의 새 기사부터 확인하는 것을 기본 정책으로
한다. 검색 제공자별 페이지 크기와 호출 비용을 고려한 내부 안전 상한을 두고, 상한에 도달해 새
기사를 모두 확인하지 못하면 실행 이력에 경고를 남기거나 다음 페이지를 이어서 처리한다. RSS/Atom
피드는 제공된 새 항목을 처리하되 소스별 안전 상한을 적용한다.
