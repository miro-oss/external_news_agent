## 0. 이 문서에 대하여

기존 계획서 두 개는 각각 1,178줄 / 1,651줄이고 서로를 참조한다. 여기에 중간시연 피드백까지
얹히면서 "지금 무엇을 만들고 있는지"를 한 번에 볼 수 없게 됐다. 이 문서가 그 하나다.

**두 문서를 대체하지 않는다.** 결정의 근거와 상세 계약은 여전히 원본에 있다. 이 문서는
*무엇을 · 왜 · 어떤 순서로* 만드는지를 한 장에 모은 것이다.

### 한 문장 요약

> 데이터의 1급 객체를 **기사에서 이슈로**, 에이전트의 역할을 **함수에서 판단 주체로** 옮긴다.

### 이 시스템이 "뉴스 요약기"와 다른 점

아이디어는 베낄 수 있지만 아래는 베끼기 어렵다. **그리고 대부분 이미 구현돼 있다** —
지금까지 설명을 안 했을 뿐이다.

| # | 축 | 지금 상태 |
|---|---|---|
| 1 | **문장 단위 근거 추적** — 요약의 모든 주장이 원문 몇 번째 문장에서 왔는지 클릭으로 확인된다 | 구현됨. 기사 상세에서 동작 (리포트 연결은 P0-5) |

1~5는 **원래부터 돌아가던 것**이고, 이번 계획으로 6~12가 더해졌다.
경쟁 관계에서 밀리지 않으려면 **1~5를 설명하는 것**이 6~11을 만드는 것만큼 중요하다.
그래서 P0에 §10 설명 문서가 들어가 있다.

> 10번이 특히 그렇다. **같은 사건을 여러 매체가 다르게 쓴다는 사실 자체가 정보**인데,
> 기사 단위로 요약하면 그게 안 보인다. 이슈로 묶어야 비로소 관측되는 값이다.

## 2. 중간시연 피드백과 진단

| 피드백 | 원인 |
|---|---|
| 요약이 너무 길어서 안 읽힘 | 기사 1건마다 독립 요약 → 같은 사건이 N번 반복. 길이 제약도 없음 |
| 관련 기사가 몇 개고 어디서 나왔는지 모름 | 기사끼리 묶는 개념 부재 |
| 똑같은 내용을 DB에 다 넣음 | dedup이 URL 완전일치 1단계뿐 |
| 한 번에 몇 건까지 / 병목을 어떻게 푸나 | §4에 수치로 답 |
| 분석기사와 리포트 차이를 모르겠다 | 같은 내용을 두 화면이 다른 입도로 두 번 보여줌 |
| 초전도체가 거짓으로 밝혀진 다음 날 중요도는? | 중요도가 기사 시점에 1회 고정 |
| 지난주에 뭐가 핫했는지 | 시간축으로 묶을 단위 부재 |
| 근거1이 어느 기사 어디인지 | 기사 상세엔 있는데 리포트로 갈 때 버려짐 |
| 리포트 키워드를 모르겠다 | 키워드가 화면에 전혀 안 나옴 |
| 위험도가 내 입장에선 안 위험 | 루브릭 없음 + 회사 맥락 없음 |
| 에이전트가 뭘 하는지 모르겠다 | 설명 부재 (데이터는 이미 쌓이는 중) |
| **에이전트 구조가 너무 단순하다** | LLM 호출 3종이 전부 단발. 판단 순서가 Java에 하드코딩 |

### 근본 원인 둘

**(1) 1급 객체가 기사다.** 기사 1건 = 분석 1회 = 리포트 항목 1개. 같은 사건을 10개 매체가
쓰면 요약이 10개 나오고 LLM도 10번 부른다.

**(2) 에이전트가 판단하지 않는다.** `analyze` / `verify` / `report` 세 호출이 전부 입력→출력
단발이다. 언제 검증할지, 무엇을 버릴지, 정보가 부족한지를 전부 Java가 정한다. 에이전트는
"정보가 부족하다"고 말할 수단조차 없다. 규칙은 촘촘한데 판단은 얕다.

단, 책임을 더 준다 ≠ 마음대로 한다. 세 가지는 안 바꾼다.

1. 에이전트는 stateless이고 DB를 모른다
2. 외부 호출(검색·크롤링)은 **Spring이 실행**한다. 에이전트는 제안만 한다
3. 모든 LLM 호출은 예약된 예산 안에서만 일어난다

(§6에서 상술)

## 4. 수집 — 얼마나 가져오고, 어떻게 아끼나

### 4-1. "한 주제당 최대 몇 건인가" (질문에 대한 답)

현재 시드는 **FEED 17개 + SEARCH 3개 = 20개**인데, §4-6에서 SEARCH를 Naver 하나로 줄이고
RSS를 늘린다. 재편 후 기준(FEED 25개 목표 + Naver 1개)으로 한 주제에 전부 연결하면:

| 소스 종류 | 개수 | 후보 범위 | 소계 |
|---|---|---|---|
| FEED (RSS) | 25 | 피드가 제공한 항목 전체 | 가변 |
| SEARCH (Naver) | 1 | `batchSize` 100 × 페이징 3회 = 300 | 300 |
| 주제 전체 선별 | — | URL 정규화·키워드 게이트·`metadataFit` 순위 | **최대 300건 / 실행** |

P1-2 전에는 소스별 `crawlPolicy.maxArticlesPerRun` 때문에 먼저 온 항목이 잘렸지만, P1-2부터는
모든 조합의 후보를 합친 뒤 키워드 필터와 URL 중복 제거를 거쳐 주제당 최대 300건을 고른다.

> **2026-08-31 결정 — `maxArticlesPerRun` 호환 정책:** 이 필드는 기존 요청·응답과 저장 데이터의
> 호환을 위해 deprecated 상태로 남긴다. 값은 저장·반환되지만 실제 수집 선별에는 사용하지 않는다.
> 운영 상한의 정본은 `news.collection.topic-article-limit`이며, 필드 삭제는 별도 breaking API 버전에서 한다.

**Naver 상한을 왜 올릴 수 있나** — `Topic.batchSize` 기본값 20은 *"커넥터 중 천장이 가장 낮은
Tavily(max_results 20)에 맞췄기 때문"*이다(`Topic.java:37-53` 주석). **Tavily를 빼면 그 제약이
사라진다.**

| 항목 | 현재 | 변경 |
|---|---|---|
| `Topic.batchSize` 기본 | 20 | **100** (Naver `display` 최대치) |
| `MAX_BATCH_SIZE` | 100 | **300** (+ DB CHECK `V24`) |
| Naver 페이징 | 없음 | `start` 파라미터로 최대 3페이지 |

**호출량 여유 확인**: 주제 10개 × 3콜 × 24회/일(60분 주기) = **720콜/일**.
Naver 일 한도 25,000 대비 3% 미만이다. 10분 주기로 당겨도 4,320콜로 여유가 있다.

> **결론: 병목은 Naver 쿼터가 아니라 LLM 예산이다.** 그래서 §4-4의 "수집은 넓게, 분석은
> 중요도 순으로"가 더 중요해진다. 수집을 늘릴수록 §4-2의 LLM 미분석 관측이 늘기 때문이다.

### 4-2. 그런데 여기에 진짜 문제가 있다

**분석 상한은 실행당 30건(FREE) / 20건(PAID)이다** (`application.yml:69-79`).

```
1,050건 수집  →  ~280건 저장  →  30건만 LLM 분석
                                  나머지 250건은 저장·관측되지만 LLM 분석과 리포트 근거에서 제외
```

여기서 **저장 실패·폐기와 LLM 미분석을 섞어 부르지 않는다.** 현재 상한은 `ANALYZE` 예약에만
걸리고, 상한 뒤의 기사는 DB와 run 관측에는 남는다. 다만 stub 결과는 LLM 근거가 아니므로 리포트의
분석 finding에서 빠진다. 진짜 문제는 **수집 관측의 약 89%가 이슈 귀속·우선순위 판단 없이 LLM 분석과
리포트 근거에서 제외**되고, 그 경계가 중요도가 아니라 "먼저 온 순서"라는 점이다.

### 4-3. P1-5 이전 병목은 분석이 아니라 근거 검증이었다

`AgentAnalysisOrchestrator.java:325-376`이 **bullet 1개마다 LLM 호출 1회 + 쿼터 예약 1건**을 쓴다.

```
P1-5 이전 실행 1회:
  분석      30콜
  근거 검증 ~60콜   ← 규칙 선판정이 절반 흡수한 뒤에도 이만큼
  리포트     1콜
  ────────────────
  합계     ~91콜   중 2/3가 검증
```

### 4-4. 처방 — 상한의 "위치"를 바꾼다

지금은 조합당 후보 상한과 분석 상한이 앞단에서 **먼저 온 순서로 대상을 정한다**. 저장·본문 확보·분석의
상한을 하나로 부르지 말고, 아래처럼 각 단계의 목적을 분리한다.

```
1. 후보는 넓게 수집     주제당 상한 300 (설정값), URL 정규화
2. 메타 점수로 선별     P1 `metadataFit`, P2 IDF `topicFit`으로 본문 확보 우선순위 결정 — 저장 여부와 분리
3. 관측을 저장          분석 여부와 무관하게 run·topic 관측을 남김
4. 본문을 확보          우선순위·HTTP 예산 안에서 FULLTEXT 확보
5. 중복군을 표시        SimHash로 같은 글을 표시하되 출처 행은 보존
6. 이슈로 묶는다        ~280건 → 이슈 ~70개
7. 상위 이슈만 분석     실행 예산에서 역산한 N개 대표 기사
8. 나머지는 집계한다    "그 외 관측 82건 · 매체 11곳" — LLM 요약이 아닌 count
```

즉 **"먼저 온 30건"이 아니라 "가장 중요한 30개 이슈"**를 분석한다.

새 설정값 (`application.yml`):
```yaml
news:
  collection:
    topic-article-limit: 300      # 주제당 수집 상한 (조합당 상한 대체)
    fulltext-limit-per-run: 300   # run 전체 본문 HTTP 요청 예산
  analysis:
    issue-limit-per-run: 30       # 실행당 분석할 이슈 수
```

### 4-5. 절감 조치와 효과

| 조치 | 효과 | 위치 |
|---|---|---|
| URL 정규화 (`utm_*`·`fbclid`·프래그먼트 제거, 호스트 소문자화) | 저장 감소. **가장 싼 개선** | `ArticleHasher.java:23-29` |
| **본문 지문(SimHash) 중복군 표시** | 전재·신디케이션의 출처 관측은 보존하고 대표만 클러스터 투표·LLM 입력에 사용 | §5-2 1.5단계 |
| 이슈 클러스터링 → 대표만 분석 | 분석 대상 150 → ~40 | §5 |
| 속보 분석 스킵 | 문장 2~3개짜리에 LLM 안 씀 | §5-4 |
| **근거 검증 배치화** | 검증 60콜 → 40콜. **단일 최대 절감** | `/v1/verify-evidence`에 `claims[]` |
| **표현 강도 사다리** | 규칙이 먼저 탈락시켜 **LLM 판정 대상과 자기 검증 대상이 같이 준다.** 비용 0 | §6-2-1 |
| 본문 크롤링 전 점수 컷 | HTTP 요청 자체를 줄임 | §7-1 |

호출량은 `N = 실행당 LLM 분석 이슈 수`, `P = 충돌 멤버 승격 수`로 계산한다.

```
개선 후 기본 운영: 이슈 ~70개 중 N=30
  분석 30 + 배치 검증 ≤30 + 승격 예상 4 + 리포트 1 = 최대 약 65콜

전체 분석 부하 시험: N=70
  분석 70 + 배치 검증 ≤70 + 승격 예상 10 + 리포트 1 = 최대 약 151콜
```

**151콜은 기본 운영값이 아니라 전체 분석 부하 시나리오다.** P1-5 이전 약 91콜과 비교할 기본 목표는
약 65콜이었고, 완료 후 run 3891에서 **51콜**로 측정됐다. 이슈 70개 모두를
LLM 분석하지 않았는데 "분석률 100%" 또는 "같은 비용으로 9배"라고 말하지 않는다.

> **2026-08-31 범위 결정:** P1-2는 분석 대상 이슈를 `issue-limit-per-run` 이하로 제한하고 세 커버리지
> 지표를 분리하는 데까지 담당한다. 위 약 65콜 목표는 근거 검증을 `claims[]`로 묶는 P1-5가 완료되어야
> 성립하므로 P1-2 완료 조건에서 P1-5 완료 조건으로 이동한다. P1-2만으로 배치 검증까지 당겨 구현하지 않는다.

> **2026-08-31 리뷰 결정:** `metadataFit` 정렬이 실제 HTTP 비용을 줄이도록 본문 확보에는
> `news.collection.fulltext-limit-per-run=300`을 둔다. 저장은 주제당 상한까지 유지하고, 본문 요청만
> run 전체 상위 300건으로 제한한다.

**승격 ~10콜을 계산에 넣어 둔다.** §5-6이 `conflicts`가 걸린 이슈만, 이슈당 1건으로 상한을
두므로 이슈의 10~15%를 잡은 값이다. `ADDS`까지 전부 승격하면 이 줄이 70이 되어 **분석 호출이
두 배가 된다** — 상한을 `conflicts`로 좁힌 이유가 이 숫자다.

분석 이슈 수(`issue-limit-per-run`)는 **주제 수가 아니라 하루 실제 run 수와 위 공식**으로 예산에서
역산한다. run 하나가 여러 주제를 포함할 수 있으므로 `주제 수 × 실행 횟수`를 곧바로 run 수로 세지 않는다.
FREE 일 1,500콜에서 기본 시나리오가 run당 최대 65콜이면 이론상 하루 23회 이하이고, 운영 여유와
실패·재시도를 감안해 기본은 **6시간 주기(하루 4회) + N=30**으로 둔다. 60분 주기는 실측 비용을 본 뒤
올린다. 수집 주기·run 수·N을 한 표에서 함께 바꾸고, `costUsd`·`credits`로 검증한다.

> ⚠️ 근거 검증 배치화는 API 계약 변경이다. `AGENTS.md`에 따라 **Notion `API 명세서`를
> 먼저 갱신**한 뒤 구현한다.

### 4-6. 소스 재편 — 유료 검색 API를 빼고 RSS를 늘린다

**무료 플랜의 검색 API는 이 용도에 못 쓴다.**

| Provider | 무료 한도 | 수집 주기 60분 기준 |
|---|---|---|
| SerpAPI | 월 100회 | 주제 1개만 돌려도 **나흘이면 소진** |
| Tavily | 월 1,000 크레딧 | 주제 2~3개면 한 달을 못 버팀 |
| Naver | 일 25,000회 / 총 775,000회 | 넉넉함 — **유일하게 실용적** |

게다가 Tavily는 `max_results` 천장이 20이라, **그 하나 때문에 `Topic.batchSize` 기본값 전체가
20에 묶여 있었다**(`Topic.java:37-53` 주석). 빼면 Naver를 제 성능으로 쓸 수 있다.
**비용은 비싸고 수확은 적으며, 남은 소스의 발목까지 잡고 있었다.**

`news_articles`에 `issue_id` FK를 **추가하지 않는다.** 한 기사가 여러 주제에 걸릴 수 있고,
`CollectionRunArticle`이 이미 관측 M:N을 담당하는 기존 설계와 일관되게 조인 테이블로 둔다.

`news_content_groups`는 **같은 글의 출처 provenance를 보존하면서 분석 대표를 하나만 고르는 장치**다.
다른 매체·URL의 행을 지우지 않으므로 `publisher_count`와 원문 링크가 유지된다. `news_issue_relations`는
"검증 실패"가 새 이슈가 됐을 때 원 이슈를 배경으로 연결하는 데 쓴다.

집계 의미도 고정한다. `article_count`는 출처 행 전체, `publisher_count`는 distinct 매체,
`independent_content_count`는 distinct content group + group이 없는 단독 기사 수다. 같은 원고를 5개
매체가 전재하면 `5 / 5 / 1`이며, 매체 수는 도달 범위로 보존하되 독립된 교차 확인 5건으로 세지 않는다.

### 5-2. 클러스터링 — LLM을 쓰지 않는다

클러스터링에 LLM을 쓰면 비용이 다시 기사 수에 비례한다. `plan-final.md` M10이
"Spring deterministic clustering"으로 못박은 방향이 옳다. 신규 `collection/cluster/IssueClusterer.java`:

| 단계 | 선행 데이터 | 방법 | 잡는 것 | 결과 |
|---|---|---|---|---|
| 1 | 수집 메타 | URL 정규화 후 완전일치 | 같은 canonical URL의 트래킹 파라미터 변종 | 기사 행 1개 + run/topic 관측 M:N 보존 |
| **1.5** | **FULLTEXT** | **본문 SimHash 해밍 거리 ≤ 3** | **URL이 다른데 본문이 같은 전재·신디케이션 기사** | **행을 지우지 않고 같은 `content_group_id` 부여** |
| 2 | 제목 토큰 | 제목 정규화 + 토큰 자카드 ≥ 초기 임계 | 같은 보도자료를 받아쓴 기사들 | 이슈로 묶음 |
| 3 | 결정론적 엔티티 | 엔티티 교집합 ≥ 2 **AND** 발행 시각 차 ≤ 48h | 제목이 다른 같은 사건 | 이슈로 묶음 |

**1단계만 동일 기사 행으로 합치고, 1.5단계는 출처 행을 보존한 채 분석 중복만 제거하며, 2·3단계는
사건 단위로 묶는다.** 이 경계를 흐리면 서로 다른 매체의 보도가 사라진다. §5-3의
`관련 12건 · 매체 5곳`이 곧 이 시스템이 파는 것이므로 cross-publisher provenance는 삭제하지 않는다.

**1.5단계를 왜 넣나** — 지금 `contentHash`는 **같은 URL의 변경 판정에만** 쓰인다
(`CollectionResultWriter.java:249`, `Article.hasSameContent`). URL이 다른 기사끼리는 비교하지 않으므로
연합뉴스 기사를 그대로 실은 포털·지역지가 전부 별개로 남는다. 완전일치 해시로는 매체가 문단 하나만
손대도 안 잡히니 **64비트 SimHash + 해밍 거리**를 쓴다. 임계는 **≤ 3**으로 아주 좁게 시작한다.
이 단계는 "같은 사건"이 아니라 **"같은 글"**만 표시하는 자리이며, content group의 대표만
클러스터 투표와 LLM 입력에 넣는다. 그룹의 모든 기사·매체·원문 링크는 응답 provenance에 남긴다.

> ⚠️ **본문이 있는 기사에만 적용한다** (`FetchStatus.FULLTEXT`). `contentHash`는 본문이 없으면
> 제목+요약으로 지문을 만드는데, 그 상태로 비교하면 제목이 비슷한 다른 기사가 병합된다. §12-8 참조.

2단계 토큰화는 `agent/app/core/evidence.py:455` `_tokens`와 **동일한 명세를 Java로 구현**한다
(2자 이상, 한국어 조사 제거, 불용어 제외). Python 함수를 호출하거나 복사본을 별도 정본으로 두지 않는다.
공통 테스트 fixture를 두 언어 구현에 적용해 결과가 같음을 검증한다. 제목에서 `[속보]` 같은 대괄호와
언론사명 접미사를 먼저 뗀다.

3단계 엔티티는 LLM 분석 결과를 기다리지 않는다. 신규 `DeterministicEntityExtractor.java`가 제목·요약·
FULLTEXT에서 **기업 사전 + 영문 대문자/제품명 패턴 + 주제 키워드 사전**으로 후보를 만들고 정규화한다.
이 결과가 클러스터 입력의 정본이며, LLM `entities`는 분석 뒤 표시·보강용이지 클러스터 키가 아니다.

**실행 순서는 고정한다.** 메타 수집·URL 정규화 → metadataFit 사전 컷 → 관측 저장 → 본문 확보 →
SimHash content group → 결정론적 토큰·엔티티 → 이슈 클러스터 → 대표 선정 → LLM 분석 순이다.
SimHash나 본문 엔티티를 본문 확보보다 앞에 놓지 않는다.

**2단계 자카드의 약점과 그 처방** — 토큰을 균등 가중하므로 "반도체"·"삼성전자"처럼 어디에나
나오는 말이 유사도를 부풀린다. §7-1의 `news_keyword_idf`(V30)가 생기면 **같은 IDF로 자카드에
가중치를 준다**(가중 자카드). 새 인프라가 필요 없고, TF-IDF 코사인이 주는 이득의 대부분을
Java 안에서 얻는다. 도입 여부는 §5-2-1의 측정으로 정한다.

> ⚠️ **2026-08-31 — 이 처방은 지금 근거가 없다.** 걱정했던 "흔한 말이 유사도를 부풀린다"가
> 홀드아웃에서 **관측되지 않았다**(precision 1.000, 오병합 0건). 균등 가중이 이미 천장이라
> 가중 자카드로 개선할 여지가 없다. 비교군 `char_wb` TF-IDF도 동률이었다.
> **가중 자카드는 실수집에서 실제로 과병합이 관측될 때만 꺼낸다.** §11-5 P2-1 참조.

### 5-2-1. 임베딩 도입 판단 — 감이 아니라 수치가 정한다 · **측정 완료 (2026-08-31)**

> ✅ **판정 완료 — 도입하지 않는다. 이 절은 종결됐다.**
> 홀드아웃(10이슈 40건)에서 **precision 1.000 / recall 1.000**. 아래 판정표의
> *"`precision ≥ 0.90` AND `recall ≥ 0.85` → 도입하지 않음. 종료."* 칸에 해당한다.
> 측정 기록: `docs/p1-1-cluster-threshold-measurement.md` · 확정값 `title-jaccard-threshold=0.50`,
> `entity-time-window=48h` (`application.yml`).
> **판정표는 측정 전에 확정했고 측정 후 바꾸지 않았다** — 결정 31의 이행 기록으로 아래를 남겨 둔다.

**Oracle `VECTOR` 임베딩은 지금 켜지 않는다.** 다만 "부족하면 붙인다"는 애매한 유보는
결국 감으로 결정하게 된다. **판단 기준을 미리 못박는다.**

**측정 대상** — `BE/src/test/resources/golden/clusters.v1.json`
실제 수집 기사 200건을 손으로 이슈에 묶은 정답셋(2주치, 반도체·제조 주제).
`IssueClusterer`가 Java에 있으므로 골든셋도 BE 테스트 리소스에 둔다.

**지표** — pairwise
- `precision` = 같은 이슈로 묶은 기사 쌍 중 실제로 같은 사건인 비율
- `recall` = 실제로 같은 사건인 쌍 중 실제로 묶인 비율

**판정표 (사전 확정, 측정 후 협상 금지)**

| 조건 | 판단 |
|---|---|
| `precision < 0.90` | **임베딩 검토 중단.** 과병합은 다른 사건을 한 요약에 섞어 리포트를 오염시킨다. 임계값을 조이는 게 먼저이고 임베딩은 이 문제를 악화시킨다 |
| `precision ≥ 0.90` **AND** `recall ≥ 0.85` | **도입하지 않음. 종료.** |
| `precision ≥ 0.90` **AND** `0.75 ≤ recall < 0.85` | **규칙 튜닝 먼저** — 자카드 0.6→0.5, 시간창 48→72h, 제목 정규화 사전 보강. 재측정 후 이 표로 되돌아온다 |
| `precision ≥ 0.90` **AND** `recall < 0.75` | 임베딩 **검토 착수** (자동 도입 아님, 아래 3개를 추가로 통과해야) |

**검토 착수 후 도입 조건 — 셋 다 충족해야 한다**

1. 규칙 튜닝을 마친 뒤에도 `recall < 0.75`가 유지된다
2. 놓친 쌍 30개를 표본 조사했을 때 **"제목도 엔티티도 실제로 안 겹치는" 케이스가 과반**이다.
   겹치는데 놓쳤다면 그건 규칙 버그지 임베딩이 풀 문제가 아니다
3. `VECTOR_DISTANCE`를 인덱스 없이 O(N²)로 돌려도 실행당 1,000건 기준 허용 시간 안에 끝난다
   (인덱스 없이 시작한다는 M0 결정 유지)

**측정 시점**: P1-1 구현 초안 직후, **완료 판정 전**. 초기 Java 구현이 pair score와 cluster assignment를
JSON으로 내보내면 §5-2-2가 그 결과를 평가한다. 홀드아웃 임계값을 `application.yml`에 반영하고
재검증까지 끝나야 P1-1 완료다. 결과는 `docs/`에 측정 기록으로 남긴다.
→ ✅ 절차대로 이행됐다. `IssueClustererGoldenExportTest` → `app.eval.cluster_sweep` →
`docs/p1-1-cluster-threshold-measurement.md` → `application.yml`.
임베딩 모델은 M0에서 확정한 in-DB ONNX `MULTILINGUAL_E5_SMALL`(384차원)이라 외부 API 비용은 0이다.
**비용이 0인 것과 도입할 이유가 있는 것은 다르다** — 파이프라인·인덱스·재색인이라는 운영 부담이
남기 때문에 위 조건을 통과할 때만 켠다.

### 5-2-2. 임계값은 곡선에서 읽는다 — scikit-learn은 측정 도구로만 쓴다 ★ · **실행 완료**

> ✅ **스윕 완료 (2026-08-31).** 자카드 `0.40~0.75` × 시간창 `24/48/72h`를 훑어
> **calibration 0.50 / 48h**를 골랐고 **홀드아웃에서 precision·recall 1.000으로 재확인**했다.
> 기존 초기값 0.60은 recall 0.600이었다 — **감으로 뒀으면 같은 사건의 40%를 놓칠 뻔했다.**
> 비교군 `char_wb` TF-IDF도 홀드아웃 1.000으로 **동률** → §11-8의 sklearn 런타임 도입은
> "격차 없음"으로 확정 보류. sklearn은 dev 의존성에만 남는다 (결정 39 유지).
>
> ⚠️ **P2-1 재측정의 실익이 사라졌다.** 아래 "토큰 가중" 행은 *P2-1 IDF 뒤 균등 vs IDF 가중 재측정*을
> 예정해 두었는데, **균등 자카드가 이미 홀드아웃 1.000이라 이길 여지가 없다.** P2-1은 수집 우선순위
> (`metadataFit` → `topicFit`) 목적만 남기고, 클러스터링 가중 재측정은 골든셋을 어렵게 다시 짤 때만 한다.

§5-2-1 판정표의 "규칙 튜닝 먼저" 칸이 *"자카드 0.6→0.5, 시간창 48→72h"*라고 적혀 있다.
**이걸 손으로 두세 번 돌려 고르는 것이 곧 '감으로 결정하는' 것이다.** 판정표를 사전 확정해 놓고
정작 임계값을 감으로 정하면 앞의 결정이 무의미해진다.

**조치**: `agent/pyproject.toml`의 `[dependency-groups] dev`에 **`scikit-learn`을 추가한다.**

| 항목 | 결정 |
|---|---|
| 위치 | **dev 의존성만.** 런타임 5개(`fastapi`/`google-genai`/`httpx`/`pydantic-settings`/`uvicorn`)는 건드리지 않는다 (§6-5) |
| 용도 | 골든 클러스터셋에 대한 **임계값 스윕과 클러스터 평가**. 그게 전부다 |
| 산출물 | `application.yml`에 박을 **숫자 하나**. 라이브러리가 파이프라인에 남지 않는다 |
| 쓰는 API | `sklearn.metrics.cluster.pair_confusion_matrix` — §5-2-1이 정의한 pairwise TP/FP/FN을 그대로 준다. 보조로 `precision_recall_curve`, `adjusted_rand_score`, `v_measure_score` |

**스윕 대상**

| 축 | 후보값 |
|---|---|
| 자카드 임계 | 0.40 ~ 0.75 (0.05 간격) |
| 시간창 | 24h / 48h / 72h |
| 토큰 가중 | **P1-1에서는 균등만.** P2-1 IDF 구축 뒤 균등 vs IDF 가중을 재측정 |
| 비교군 | `TfidfVectorizer(analyzer='char_wb', ngram_range=(2,4))` + 코사인 |

`char_wb` n-gram을 쓰면 형태소 분석기 없이 한국어 유사도가 나온다. **비교군일 뿐이다.** Python이
Java feature·cluster 로직을 재구현하지 않고, Java가 내보낸 pair score/assignment와 비교군만 평가한다.
P2-1 재측정에서 IDF 가중이 이기면 Java 쪽 weighted Jaccard에 반영한다.

**런타임에 넣지 않는 이유 셋**
1. 클러스터링은 Java에 있다(§5-2, §12-6). 파이썬으로 옮기면 실행 경로에 서비스 홉이 하나 는다
2. §7-1이 IDF를 Oracle(`news_keyword_idf`)에 두기로 했다. sklearn이 IDF를 또 계산하면 **정본이 둘**이 된다
3. 에이전트는 stateless이고 DB를 모른다(§16). 클러스터링은 DB 전체를 봐야 하는 작업이라 경계를 넘는다

> 학습 기반 판단(근거 검증 임계값 학습, 중요도 가중치 학습)을 sklearn으로 하는 안은 **§11-8로 보류**했다.
> 라벨 수가 모자라고, 설명 가능성을 잃는다.

### 5-3. 이슈 단위 요약

대표 기사 1건만 `/v1/analyze`에 보낸다. 대표 선정은 결정론적(LLM 0회):
`본문 길이 ≥ 500자` → `Source.reliabilityScore` → `발행 시각 빠른 순`.

멤버 기사는 **원칙적으로 분석하지 않는다.** 예외는 §5-6이 정하는 승격 1건뿐이다.

화면에는 `관련 12건 · 매체 5곳`으로 나온다 — "몇 갠지, 어디서 나왔는지"의 직접적 답.

> ⚠️ **선후 함정** — 이전 판은 *"새 사실을 더하는 경우(`stance = ADDS`)만 이슈 요약을 갱신한다"*고
> 적었는데, **`stance`를 알려면 그 기사를 분석해야 한다.** "분석 안 한 기사의 stance를 보고 분석
> 여부를 정한다"는 순환이다. §5-6이 이 고리를 끊는다.

### 5-4. 속보와 후속 추적

**감지** (신규 `BreakingNewsDetector.java`, `StubArticleAnalyzer.java:124-156`의 키워드 매칭 패턴 재사용):
다음 둘 중 하나일 때만 속보로 본다.

1. 제목에 `[속보]` `[1보]` `breaking` `urgent`가 있다. **`[단독]`은 단독 취재 표시이지 속보가
   아니므로 `soleSource` 신호로만 쓴다**
2. 발행 2시간 이내 **AND** `FetchStatus.FULLTEXT` 성공 **AND** 본문 300자 미만이다

`METADATA_ONLY`·`FULLTEXT_BLOCKED`·`FAILED`의 짧은 텍스트는 페이월·추출 실패·teaser일 수 있으므로
속보로 분류하지 않는다.

**처리**: 개별 LLM 분석을 하지 않고 이슈에 `role = BREAKING`으로 붙인다. 문장 2~3개짜리는
근거 검증이 무의미하고 비용만 나간다. 후속 상세 기사가 오면 그때 대표로 승격해 분석한다.

**후속 추적은 별도 기능이 아니라 이슈 클러스터링 그 자체다.**
속보가 이슈를 만들고, 후속은 같은 이슈에 붙는다. "후속이 나왔다" = "이슈에 멤버가 추가됐다".
추적기를 따로 만들지 않는다 — 이게 이슈 도입의 또 다른 이득이다.

### 5-4-1. ⚠️ 용어 충돌 — 지금 화면의 "후속"은 다른 뜻이다

지금 리포트 화면이 `ChangeType.UPDATED`를 **"후속"**으로 표시하고 있다
(`ReportsPage.tsx:118`, `:280`). 그런데 `UPDATED`의 실제 뜻은 이것이다:

> `ChangeType` 주석: *"기사 자체의 속성이 아니라 **관측의 속성**이다 — 같은 기사가 run 42에서는
> NEW이고 run 43에서는 UPDATED일 수 있다."*
> `CollectionResultWriter.java:242-272`: 같은 `urlHash`인데 `contentHash`가 달라졌을 때 `UPDATED`

주된 의미는 **같은 기사(같은 URL)의 본문이 수정된 것**이다. 오탈자 정정이나 문단 추가가 여기 들어간다.
다만 전문 확보 재시도가 성공하면 본문 변경이 없어도 분석 파이프라인이 `UNCHANGED` 관측을
`UPDATED`로 승격해 재분석한다. 어느 경우든 §5-4의 "후속 보도"(**다른 URL의 새 기사**가 같은
이슈에 붙는 것)와는 전혀 다르다.

리포트에서 `후속 3건`을 보면 누구나 "후속 보도가 3건 나왔다"고 읽는다. **지금 라벨은 오해를 부른다.**

**정리 (P0에서 처리)**

| 개념 | 데이터 | 새 라벨 |
|---|---|---|
| 같은 기사가 수정되거나 전문 확보 후 재분석됨 | `ChangeType.UPDATED` | **"갱신"** |
| 같은 이슈에 다른 기사가 추가됨 | `news_issue_articles` 신규 행 | **"후속 보도"** |

`ReportsPage.tsx`의 통계 칸과 배지 라벨을 모두 **"갱신"**으로 바꾼다.
`ChangeType` enum과 API 계약(`NEW`/`UPDATED`)은 **건드리지 않는다** — 표시 라벨만 고친다.
BE의 `ReportLabels.java`가 *"화면(FE)이 쓰는 라벨과 같은 말을 써야 같은 값이 두 이름으로
불리지 않는다"*고 못박아 뒀으므로, 리포트 본문 라벨도 함께 맞춘다.

다만 속보는 본문이 짧아 토큰이 적고 자카드가 안 나온다. 그래서 속보 전용 매칭 규칙:
- 마커(`[속보]` 등)를 뗀 핵심구 + 엔티티로만 비교
- 시간창을 48시간 → **6시간**으로 좁힌다 (속보 후속은 빨리 온다)

**민감도 높은 속보의 후속 알림** — `news_watches` (**V27로 구현 완료, P1-4 / #112**):
```sql
news_watches
  id, watch_type(BREAKING | DISPUTED | HIGH_SENSITIVITY | HYPOTHESIS | MANUAL),
  issue_id, sensitivity_at_watch, notify_group_id,
  cooldown_until, expires_at, active_yn
```
- ✅ P1-4에서는 **제목에 명시적 속보 마커가 있는 기사만** `BREAKING` watch 자동 등록. 본문이 짧다는
  이유만으로는 watch를 만들지 않는다 (`BreakingNewsDetector.hasExplicitMarker`)
- ✅ P2-2에서 `sensitivityScore ≥ 70`인 속보에 `HIGH_SENSITIVITY` watch를 추가했다
  — `watch_type` CHECK와 `sensitivity_at_watch` 컬럼은 V27을 재사용하고 #130에서 등록 경로를 켰다
- ✅ 같은 이슈에 새 기사가 붙으면 알림 발송. **M6 알림 채널(텔레그램/이메일)을 그대로 재사용**
  (`WatchNotificationDeliveryService`가 `NotificationSenderRegistry`를 공유한다)
- ✅ 알림 문구 예: `"2시간 전 속보 'HBM4 증설'에 후속 3건 · 매체 3곳 확인됨"` /
  `"⚠ 'OO 실적 전망'에 반박 기사 등장"`
- ✅ 만료 48시간, 쿨다운 30분 (M12 버스트 감지의 쿨다운 규칙 재사용)
- ✅ P2-3에서 `DISPUTED` 상태 진입 시 48시간 watch를 등록하고 상태가 되돌아오면 비활성화한다.
  후속 알림 조회에도 `DISPUTED`를 포함하고 반박 알림 문구를 분기했다
- ⏳ `HYPOTHESIS`(A12) watch_type은 CHECK에만 있고 등록 주체가 아직 없다

이 테이블은 `plan-agent-final.md` §14-4의 가설 추적(`news_insight_watches`)과 메커니즘이 같다.
**하나로 합치고 `watch_type`으로 구분한다.**

### 5-5. 이슈 상태 — 초전도체 질문의 답 · ✅ **P2-3 완료 (#132)**

> **구현 결과 (2026-09-02)** — V25의 `news_issues.status`·`importance_score`·
> `news_issue_status_history`·`news_issue_relations`·기사별 stance 저장 구조를 그대로 사용했다.
> `IssueClusterWriter`의 고정 `SUPPORTS/1.0` 기록은 `IssueStanceClassifier`로 교체했고,
> 클러스터 갱신·교차 비교·승격 분석·대표 민감도 갱신에서 같은 projection을 다시 계산한다.

상태를 한 방향 화살표로만 전이시키지 않는다. **기사 추가·재분석·정정 때마다 현재 근거에서 다시 계산하는
projection**으로 둔다. 근거가 정정되면 `DISPUTED → CORROBORATED`처럼 되돌아갈 수 있고, 변경 이력은
`news_issue_status_history`에 남긴다.

새 기사가 이슈에 붙으면 `IssueStanceClassifier.java`가 제목·요약의 공통 사실 토큰, 숫자 차이,
부정·정정 표현으로 `stance_source=RULE` 후보와 confidence를 만든다. 교차 비교의 RULE 결과는 같은
계약으로 갱신하며, 대표·승격 분석에서 확인된 stance는 기존 경로대로 `stance_source=LLM`으로 보존한다.
정정 기사가 대표로 바뀌어도 가장 이른 비정정 기사를 stance 기준으로 유지한다.

재계산 규칙은 우선순위가 높은 것부터 적용한다.

| 우선순위 | 조건 | 계산 상태 |
|---|---|---|
| 1 | 서로 다른 매체·독립 content 2건 이상 **LLM 확인** `RETRACTS`, 또는 등록된 공식 발표 도메인의 정정 | `RETRACTED` |
| 2 | **LLM 확인** `DISPUTES` 1건, 또는 서로 다른 매체·독립 content가 포함된 `crossSource.conflicts` | `DISPUTED` |
| 3 | 서로 다른 매체 2곳 **AND 독립 content 2건 이상** confidence ≥ 0.8 `SUPPORTS`이고 1·2 조건 없음 | `CORROBORATED` |
| 4 | 위 조건 미충족 | `EMERGING` |

`RULE RETRACTS` 하나만으로는 `RETRACTED`를 만들지 않는다. "원 발표 주체의 정정"은 아무 고신뢰
매체가 아니라 **이슈 엔티티와 매핑된 공식 도메인 allowlist**에서 온 기사만 인정한다.
구현에서는 등록된 `FEED` 소스 이름에 이슈 엔티티가 매핑되고 기사 host가 소스 `url_template` host와
일치할 때만 공식 도메인으로 판정한다. 검색 결과의 원문 도메인을 임의로 공식 소스로 승격하지 않는다.

**초전도체 질문의 답:** 거짓으로 밝혀진 다음 날, 원래 이슈는 `RETRACTED`로 `statusPenalty`를
받아 중요도가 급락한다. 그런데 **"검증 실패" 자체가 새 이슈로 승격**된다 — 그게 그날의 진짜
뉴스이기 때문이다. 새 이슈에서 원 이슈로 `REFUTES` 관계를 만들고, 원 이슈는 UI에서 배경 링크로 남는다.

즉 중요도의 기준은 **"이 사건이 지금 무엇으로 밝혀졌는가"**이지 "며칠 전에 얼마나 화제였나"가 아니다.

### 5-6. 이슈 안에서 기사들을 맞대본다 — 기본 요청 안에서 ★ · ✅ **P1-9 완료 (#114, PR #116)**

> P1-1에서 깔아 둔 `news_issues.cross_source` CLOB·`IssueCrossSource`·FE 타입에 P1-9가 실제 값을
> 채웠다. `/v1/analyze` 요청·응답 계약 확장, `crossSource` 저장, 충돌 기사 최대 1건 승격,
> Notion 이슈 상세·`agent/README.md` 계약까지 #114에서 완료했다.

§5-3이 남긴 순환("분석해야 stance를 아는데, stance를 봐야 분석 여부를 정한다")과,
*"여러 출처가 공통으로 말하는 것 / 한 출처에만 있는 것 / 서로 충돌하는 숫자 / 빠진 이해관계자"*를
보고 싶다는 요구는 **같은 문제다.** 둘 다 "이슈 안의 기사들을 서로 맞대보는 자리"가 없어서 생긴다.

**해법은 `plan-agent-final.md` §14-3이 이미 쓴 패턴이다 — 같은 호출에서 뽑는다.**

대표 기사를 분석할 때 **멤버들의 제목·요약·매체를 같은 요청에 함께 넣고**, 출력에 두 필드를 더한다.

```json
"crossSource": {
  "consensus":           ["여러 매체가 공통으로 말하는 것"],
  "soleSource":          [{ "articleId": 412, "text": "이 매체에만 있는 주장" }],
  "conflicts":           [{ "articleIds": [401, 412], "text": "3조 vs 5조로 갈린다" }],
  "missingStakeholders": ["B사 입장", "정부 공식 발표"]
},
"promoteCandidates": [412]
```

| 항목 | 결정 |
|---|---|
| 비용 | 대표 분석 요청에 cross-source 출력을 붙이는 **기본 추가 호출은 0회**. 다만 입력·출력 토큰이 늘어 provider `credits`·`costUsd`가 오를 수 있고, 승격 분석은 `P`회 추가된다. 둘 다 `agent_runs`로 실측한다 |
| 근거 | 비용·context 상한 때문에 대표 요청에는 멤버 **제목·요약만 넣는다**. 원문이 저장돼 있어도 crossSource 값은 제목·요약 수준 관측이므로 `factual_mismatches`를 적용하지 않는다 |
| 승격 | `conflicts`에 걸린 멤버만, **이슈당 최대 1건**을 `/v1/analyze`로 올린다 |
| 사전 컷 | 승격 후보는 LLM 전에 한 번 걸러낸다 — 멤버 제목·요약에 대표 기사에 없는 **숫자·기업명·부정어**가 있는 것만 (`evidence.py`의 `_numbers` / `_companies` / `_polarity_mismatch` 재사용, LLM 0회) |
| `stance` | 모든 멤버에 RULE 후보+confidence를 남기고, 대표·승격 기사만 LLM 확인값으로 덮어쓴다. API가 `stanceSource`를 함께 내려 관측과 확인을 구분한다 |

**왜 `conflicts`만 승격하나** — `soleSource`(단독 보도)는 흥미롭지만 틀려도 손해가 작다.
`conflicts`는 **리포트에 서로 다른 숫자가 나란히 실릴 위험**이라 확인 비용을 쓸 값어치가 있다.
새 사실을 더하는 기사를 전부 승격하면 분석 호출이 이슈 수의 2배가 된다 —
§4-5의 `승격 ~10콜`이 70콜이 되어 실행당 계산이 통째로 깨진다.
단독 보도까지 승격하는 안은 §11-8에 보류로 남겼다.

> `missingStakeholders`는 §6-3 조사 루프의 **입력이 된다.** "무엇이 부족한가"를 별도 호출로 다시
> 묻지 않고 여기서 이미 뽑아 두는 것이다. 조사 루프의 트리거를 결정론적으로 유지할 수 있게 된다.

> ⚠️ 이 두 필드는 `analyze` 응답 계약 변경이다. §17 표에 추가했다.

예: 원문 "투자를 검토 중" → 요약 "대규모 투자 결정". 숫자도 기업명도 안 틀렸지만 사실이 아니다.

새 엔드포인트가 필요 없다. `/v1/analyze`에 `selfCritique: true` 플래그를 더한다.

**★ 적용 범위를 이슈 단위에서 주장 단위로 좁힌다.** 이전 판은 *"중요도 상위 N개 이슈"* 전체에
걸었는데, 그러면 이미 규칙으로 확정된 주장까지 다시 LLM을 태운다. **§6-2-1이 들어오면 위 예시의
대부분이 규칙층에서 끝나므로**, 자기 검증은 아래 조건을 만족하는 주장에만 건다.

```
(1) P1 임시 우선순위가 상위 구간
        · topicFit + 매체 수 + 최신성 + sensitivityScore≥70
        AND
(2) 규칙층이 확정하지 못했다              또는  (3) 출처 간 결론이 갈린다
    · assess_with_decisive_rules 미통과            · §5-6의 conflicts에 걸림
    · §6-2-1의 강도 차가 1단계 (= weak, 애매한 구간)
```

**(1)은 필수고 (2)·(3) 중 하나가 더 있어야 한다.** 중요하지 않은 이슈의 애매한 주장에까지
+1콜을 쓰지 않는다. 전체에 걸면 비용이 2배가 된다. P1-7의 임시 우선순위는 P2-3에서
저장된 `importanceScore` 내림차순으로 교체했고 상위 20% 제한은 유지한다.

### 6-2-1. 레벨 1이 오기 전에 규칙이 먼저 깎는다 — 표현 강도 사다리 ★ · ✅ **P1-5 완료 (#120)**

> **기준선이 이 규칙을 기다리고 있다.** `falsePassRate` 0.133을 만든 통과 2건이 둘 다
> 강도 과장(`modality-*`) 유형이다 (§13). 사다리가 잡아야 할 대상이 이미 라벨로 특정돼 있다.

§6-2가 든 예시("검토 중" → "결정")를 다시 보면, **이건 의미 추론이 아니라 어휘의 단계 문제다.**
LLM을 부르지 않고 사다리로 잡을 수 있다. 지금 `evidence.py`의 규칙층(`factual_mismatches`)은
숫자·날짜·기업명·부정 반전까지만 보고 **동사의 확정 단계는 보지 않는다.**

```
0 관측·보도  →  1 검토·논의  →  2 계획·추진  →  3 발표·공식화
             →  4 승인·계약·확정  →  5 착수·시작  →  6 완료·양산
```

**판정**: `주장의 최고 단계 − 근거의 최고 단계`

| 차 | 판정 | 예 |
|---|---|---|
| ≤ 0 | 통과 (근거가 주장보다 세거나 같다) | 근거 "착수했다" / 주장 "추진 중" |
| = 1 | **`weak`** — 애매한 구간. §6-2 자기 검증 대상 | 근거 "발표했다" / 주장 "승인됐다" |
| ≥ 2 | **`ungrounded`** — 과장으로 탈락 | 근거 "검토 중" / 주장 "결정했다" |

| 항목 | 결정 |
|---|---|
| 위치 | `agent/app/core/evidence.py`에 `_MODALITY_LADDER` + `modality_overreach()`. **`factual_mismatches`와 같은 4-1 층**에서 호출 (§10) |
| 비용 | **0.** LLM을 부르지 않는다 |
| 한국어 어미 | 기존 `_strip_korean_suffix`(`evidence.py:464`)를 그대로 재사용한다. 사다리를 새 토크나이저로 만들지 않는다 |
| 조건·전망 표현 | "가능성", "전망", "~할 수도"가 붙으면 **주장의 단계를 0으로 내린다.** 안 그러면 "결정할 가능성"이 4단계로 잡혀 오탈락한다 |
| 재사용 | §8-7의 리포트 재검증이 **같은 사다리**를 쓴다 |

**왜 학습 모델이 아니라 규칙인가** — 6단계 순서형이라 학습할 파라미터가 사실상 없고, 무엇보다
**떨어진 이유를 화면에 한 줄로 쓸 수 있어야 한다**(`"근거는 '검토 중'인데 요약은 '결정'입니다"`).
§16이 유지하기로 한 *"기계가 판정할 수 없는 것은 판정하지 않는다"*의 짝은
**판정할 수 있는 것은 설명 가능하게 판정한다**이다.

> ⚠️ 이 규칙은 **정상 요약을 떨어뜨릴 수 있다**(오탈락). 사다리 사전이 부실하거나 조건절을
> 못 읽으면 그렇게 된다. 그래서 §13의 골든셋 negative case가 **선행 조건**이다(P1-0).
> **사전을 넓히기 전에 측정 장치부터 만든다.** 시작은 좁게, 넓히는 건 숫자를 보고.

### 6-3. 레벨 2 — 조사 루프 (Plan-Act-Observe) · ⏳ P2-5 (선행 P2-4 spike, P1-9, V33)

`plan-agent-final.md` A7 `/v1/explore`를 실제로 구현한다. **에이전트는 도구를 실행하지 않고
제안만 하고, 실행은 Spring이 기존 수집 경로로 한다.** 이 경계는 기존 계획의 핵심 결정이고 옳다 —
감사 로그와 쿼터가 한 곳에 남아야 하기 때문이다.

도구 4개:

| 도구 | 뜻 |
|---|---|
| `SEARCH_MORE(query, reason)` | "이 이슈는 A사 입장만 있다. B사 반응을 찾아야 한다" |
| `READ_FULLTEXT(articleId)` | 메타데이터만 있는 기사의 본문을 읽자 |
| `COMPARE_HISTORY(entities, days)` | 과거 유사 이슈와 비교하자 |
| `CONCLUDE(reason)` | 충분하다 |

트리거는 전부 결정론적이다 (에이전트가 아무 때나 루프를 돌 수 없다):
- 이슈 중요도 상위 N **이면서** 근거 문장 수 < 임계
- 이슈 상태가 `DISPUTED`
- 속보가 24시간 단독
- §5-6의 `missingStakeholders`가 비어 있지 않다 ← **별도 호출 없이 이미 뽑아 둔 값**

**제안을 실행할지는 Spring이 검사한다.** 에이전트의 제안은 요청이지 명령이 아니다.

| 가드 | 규칙 | 왜 |
|---|---|---|
| 반복 상한 | `maxSteps = 3`, 이슈당 1일 1회 | 무한 루프 차단 |
| 예산 상한 | 조사 루프 전체가 **일 예산의 15% 이내** | 정규 분석을 굶기지 않는다 |
| **중복 검색 금지** | 제안 쿼리를 정규화(소문자·공백·조사 제거)해 해시로 두고, **같은 run에서 이미 실행한 쿼리면 거절** | 에이전트가 표현만 바꿔 같은 검색을 반복한다 |
| **허용 소스만** | `allowedSources` 화이트리스트 밖이면 거절. 현재는 **Naver 검색 + 활성 FEED**뿐 (§4-6) | 비활성화한 유료 API를 에이전트가 되살리지 못하게 |
| 예산 처리 | **승인 시 예약이 먼저, 실행이 나중.** 기존 쿼터 예약·정산(A3)을 그대로 탄다 | 실패해도 예산이 새지 않는다 |
| **거절 기록** | 거절도 `agent_runs`에 `rejection_reason`으로 남긴다 | 거절은 감사 대상이다. 왜 조사를 안 했는지 화면(§9)과 지표(§13)가 이 값을 읽는다 |

거절되면 **현재 근거만으로 리포트 단계로 넘어간다.** 조사 실패가 리포트 실패가 되면 안 된다.

**종료 조건 — 셋 중 하나라도 걸리면 끝낸다**

1. 에이전트가 `CONCLUDE`를 반환한다 (정보가 충분하다는 판단)
2. `maxSteps` 또는 예산 15% 상한에 닿았다
3. **추가 수집분에서 이슈의 근거 문장 수가 늘지 않았다** ← 이게 없으면 상한까지 헛돈다

3번이 실질적인 종료 조건이다. 1·2번은 각각 에이전트와 예산이 정하지만, **"더 찾아봐도 새 근거가
안 나온다"는 사실은 결정론적으로 관측된다.** 조사 성공률(§13)의 분자도 이 값이다.

**이게 "책임을 더 준다"의 핵심이다.** 에이전트가 "나는 아직 모르겠다"고 말할 수 있게 된다.
단, **모르겠다고 말할 수 있는 것과 마음대로 찾아보는 것은 다르다** — 위 표가 그 경계다.

### 6-4. 레벨 3 — 역할 분리 (같은 모델, 다른 책임) · ✅ **편집자·최종 재검증 완료 (P1-8, #120)**

프로세스나 프레임워크를 늘리는 게 아니라 **프롬프트 역할을 나눈다.**

| 역할 | 하는 일 | 언제 | 비용 |
|---|---|---|---|
| **수집 전략가** | 지난 주기 결과를 보고 다음 주기 키워드를 제안 | 주기당 1회 | 1콜 |
| 분석가 | 현재 `analyze` | 이슈당 1회 | 기존 |
| **검증관** | 분석가 결과를 반박 시도 (레벨 1) | 상위 이슈만 | +1콜 |
| **조사관** | 도구 제안 (레벨 2) | 트리거 시 | ≤3콜 |
| **편집자** | 리포트 톤·길이·중복 정리 | 리포트당 1회 | 기존 report에 흡수 |

**수집 전략가**가 특히 가치 있다. `plan-agent-final.md` §5-3 이관 목록의 "키워드 진화"가
미착수인데 이게 그 자리다. 지난 주기에 어떤 키워드가 노이즈만 물어왔는지, 어떤 새 엔티티가
반복 등장했는지를 보고 필수/선택 키워드를 제안한다.
**사람이 승인해야 반영된다 — 자동 반영 금지.**

**편집자**는 "요약이 길다"는 피드백의 마지막 방어선이다. 스키마 길이 제한(§8-1)이
1차 방어이고, 편집자가 리포트 전체를 보고 중복 문장을 걷어낸다.

### 6-5. 에이전트 프레임워크 재검토 · 결정 유지 (LangGraph 미도입 / PydanticAI는 P2-4 spike 미실시)

기존 계획 §13-9는 **LangChain/LangGraph만** 보고 "미도입"으로 닫았다. 그건 검토 범위가 좁았다.
프레임워크는 그 둘만 있는 게 아니므로 다시 연다.

**먼저: 지금 우리가 직접 만들어 쓰는 것**

`structured_call.py`(구조화 출력 + schema repair 1회) · `guarded_provider.py`(동시성 가드 +
크레딧 하드캡) · `rate_limit_provider.py`(429 백오프) · `breaker.py`(서킷브레이커) ·
`router.py`(플랜별 provider 선택). 의존성은 `fastapi` / `google-genai` / `httpx` /
`pydantic-settings` / `uvicorn` **다섯 개뿐**이다.

즉 프레임워크가 주는 것의 상당 부분을 이미 갖고 있다. 부족한 건 **레벨 1의 멀티턴**과
**레벨 2의 툴 콜링**뿐이다.

**결정적 사실 (코드로 확인함)**: Mindlogic 게이트웨이는 **OpenAI Chat Completions 호환**이다.
`mindlogic_provider.py:33-72`가 `{base_url}/chat/completions/`에 `messages[]`와
`response_format: {type: "json_schema", strict: true}`를 보내고 `choices[0].message.content`를
읽는다. **OpenAI 호환 엔드포인트를 지원하는 프레임워크라면 그대로 붙는다.**

**후보 평가**

| 후보 | 적합성 | 판단 |
|---|---|---|
| **PydanticAI** | Pydantic 스키마가 이미 우리 SSOT. **명시적으로 stateless** — run을 `message_history`로 재구성하므로 우리 아키텍처와 정확히 일치. Gemini 네이티브 + OpenAI 호환 `base_url` 지원. `output_type` 유니온으로 "툴 제안 or 종료" 패턴을 타입으로 표현 가능 | **1순위 후보. 단 spike 필요** |
| LangGraph | 그래프 상태를 프레임워크가 소유 → 우리는 상태가 Oracle에 있어 **이중화** | 미도입 유지 |
| Burr | 상태 저장을 외부에 위임 가능해 궁합은 좋으나, LLM 추상화가 없어 provider는 그대로 유지해야 하고 Spring이 이미 하는 상태 머신을 한 겹 더 얹음 | 불필요 |
| Google ADK | Gemini에 결합. provider가 2개인 우리와 안 맞음 | 부적합 |
| OpenAI Agents SDK | OpenAI 우선. Gemini는 별도 어댑터 필요 | 부적합 |
| 프레임워크 없이 확장 | 이관 위험 0, 골든셋 기준선 영향 없음. 대신 멀티턴·툴 스키마를 직접 작성·유지 | **레벨 1까지는 이쪽이 낫다** |

**권고 — 시점을 나눈다**

- **레벨 1(자기 검증)은 프레임워크 없이 한다.** `message_history`를 배열에 쌓고 한 번 더
  호출하는 게 전부라 50줄 안쪽이다. 여기에 의존성을 들이는 건 과하다.
- **레벨 2(툴 루프)를 만들 때 PydanticAI spike를 먼저 한다.** 툴 스키마 생성·검증과
  타입 유니온 출력은 직접 만들면 실수하기 좋은 부분이고, 여기서 프레임워크 이득이 실제로 크다.

**spike가 반드시 확인할 것 3개** (전부 우리 예산·계약과 직결된다)

1. `/chat/completions/` **끝 슬래시** — PydanticAI는 슬래시 없이 호출한다. 404/리다이렉트 여부
2. `usage.credits` 추출 — Mindlogic이 비표준 필드로 크레딧을 준다(`mindlogic_provider.py:81-88`).
   **우리 예산 시스템의 정본**이라 이걸 못 읽으면 도입 불가
3. `_UNSUPPORTED_STRICT_SCHEMA_KEYS` 제거 로직(`maxLength`·`maxItems` 등)을 프레임워크가
   생성하는 스키마에도 다시 적용할 수 있는지

**어느 쪽을 고르든 안 바꾸는 것**

- 기존 가드(`guarded_provider` / `breaker` / `rate_limit_provider` / 쿼터 예약)는 **유지한다.**
  프레임워크 자체 재시도는 **끈다** — 기존 계획 §11이 이미 "retry 중첩"을 리스크로 잡아뒀다
- `AnalyzeProvider` 인터페이스를 남겨 mock provider와 골든셋 replay가 그대로 돈다
- **오케스트레이션은 Spring, 판단은 에이전트.** 신규 `IssueInvestigationOrchestrator`가
  plan-act-observe 루프를 돌리고 매 step에서 에이전트에게 "다음에 뭘 할까"를 묻는다.
  상태·감사(`agent_runs`)·예산이 한 곳에 남는다

이 마지막이 핵심이다. **프레임워크를 쓰느냐 마느냐보다, 상태를 누가 갖느냐가 더 중요한 결정이다.**

### 7-1. 키워드 매칭 정규화 · ✅ P2-1 (#126/PR #127, V30)

**문제**: `TopicKeywordFilter.java:23-57`은 `contains()` 기반 AND/OR/NOT **게이트**일 뿐 점수가
없다. 선택 키워드 20개짜리 주제는 1개만 맞아도 통과하고, 3개짜리 주제와 비교가 불가능하다.

**설계**: 필수(AND)·제외(NOT)는 게이트로 유지하고, 선택(OR)만 **IDF 가중 매칭 비율**로 정규화한다.

P1-2에서 먼저 도입한 `metadataFit = matched optional 수 / optional 수`의 균등 비율을 P2-1에서 아래
IDF `topicFit`으로 교체했고, 동일 run 표본의 순위 변화를 기록했다. optional이 없으면 1.0을 유지한다.

```
topicFit = Σ idf(k) for matched k  /  Σ idf(k) for all optional k     (0~1)
idf(k)   = log((N + 1) / (df(k) + 1)) + 1
```

`N`과 `df`는 최근 30일·같은 language의 저장 기사 corpus에서 구하고 일 1회 갱신한다(LLM 0회).
`+1` smoothing으로 전체 문서에 등장하는 키워드와 빈 corpus에서도 0으로 나누지 않는다. optional keyword가
비어 있으면 AND/NOT 게이트 통과 후 `topicFit=1.0`으로 둔다. 흔한 키워드("반도체")는 낮게,
희귀 키워드("HBM4")는 높게 잡혀 **주제 크기와 무관하게 점수가 비교 가능**해진다.

쓰이는 곳: 본문 크롤링 전 하위 컷(§4-5), 이슈 중요도의 한 항(§7-3).

구현 측정: `docs/p2-1-topic-fit-measurement.md` — 동일 run 후보 순위 역전, 20개/3개 키워드 주제의
동일 척도 비교, 24시간 갱신 경계와 Oracle CLOB 집계를 기록했다.

### 7-3. 이슈 중요도 · ✅ P2-3 (#132)

```
importance = 0.40·sensitivity + 0.20·volume + 0.15·diversity
           + 0.15·recency + 0.10·topicFit − statusPenalty
```

- `volume` = `log(1 + 기사수) / log(11)`로 정규화하고 기사 10건에서 포화
- `diversity` = `(independentContentCount / articleCount) × min(publisherCount / 3, 1)`
  — 같은 원고의 전재 5건은 매체 도달 범위는 남지만 독립 확인 다양성은 낮게 계산된다
  → **한 매체가 10번 쓴 것보다 10개 매체가 1번씩 쓴 게 중요하다**
- `recency` = 최신 기사 기준 24시간 반감기 지수 감쇠
- `topicFit` = 같은 이슈 기사들의 P2-1 IDF 점수 평균
- `statusPenalty` = `DISPUTED` −20, `RETRACTED` −50

전부 SQL·Java로 계산되고 **LLM 추가 호출 0회**.

입력이 이미 짧은 이슈 요약이라 토큰 부담이 작다.

### 8-7. 리포트에 담기는 것과 최종 재검증

**담기는 것 — 대부분 이미 자리가 있다.** 새로 만드는 건 두 칸뿐이다.

| 담을 것 | 어디서 오나 | 상태 |
|---|---|---|
| 확인된 사실 | `importantEvents` 중 `근거 확인` | ✅ 있음 |
| 전망 | `claimType = FORECAST` (§14) | ✅ P1-5 (#120) |
| **여러 출처가 공통으로 말하는 것** | §5-6 `consensus` | ✅ P1-9 (#114) |
| **상충 보도** | §5-6 `conflicts` | ✅ P1-9 (#114) |
| 위험 요소 | `sensitivityScore` 4축 (§7-2) | ✅ P2-2 (#130, 대표 분석 점수를 `news_issues.sensitivity_score`에 반영) |
| 추가로 지켜볼 것 | `watchItems` | ✅ 있음 |
| 근거 부족으로 뺀 것 | `sourceNotes` — `"근거 부족 3건 제외, 페이월 2건"` | ✅ 있음 (§10 5단계). P1-2에서 `report_excluded_finding_ids`로 기계 판독 가능해짐 |

**상충 보도를 싣는 것이 이 리포트의 성격을 정한다.** 숫자가 갈리는 걸 숨기고 하나만 고르면
요약기고, 갈렸다는 사실을 보여주면 판단 근거다. §5-6 없이는 애초에 관측되지 않던 값이다.

**최종 재검증 — 세 가지를 본다**

`report_grounding.py`가 지금 보는 건 첫 줄뿐이다. 나머지 둘을 더한다.

| # | 검사 | 상태 |
|---|---|---|
| 1 | 근거 없는 내용이 들어갔는가 | ✅ `_limit_unsupported_significance` — 있음 |
| 2 | **`근거 약함`을 확정 사실처럼 썼는가** | ✅ P1-8 — §6-2-1 사다리 재사용 (#120) |
| 3 | **전망을 사실처럼 썼는가** | ✅ P1-5 `claimType` + P1-8 최종 재검증 (#120) |

2번이 §6-2-1을 재사용하는 이유는 같은 문제이기 때문이다. 기사 단계에서 `weak`로 강등된 주장이
리포트 문장에서 "~로 확정됐다"가 되면 **강등이 무의미해진다.** 사다리를 한 번 만들어 두 군데서 쓴다.

> `claimType`을 P1-5로 당겼으므로 P1-8은 세 검사를 모두 완료해야 한다. P1-5보다 먼저 P1-8을
> 착수해 반쪽 검증을 배포하지 않는다.

> 개발 용어를 쓰지 않는다 — 읽는 사람은 개발자가 아니다.

### 전체 흐름 — 설정에서 리포트까지

검증 5단계(아래)는 이 흐름의 3~5번 자리다. **먼저 전체를 한 장으로 본다.**

| | 단계 | 하는 일 | 지금 |
|---|---|---|---|
| **1** | **설정** | 관심 주제, 필수·선택·제외 키워드, 수집원(RSS·네이버 검색), 실행 주기, AI 플랜을 사람이 정한다 | 주기는 저장만 됨 (P2-9) |
| **2** | **수집** | 같은 요청이 두 번 돌지 않게 확인하고, 쓸 수 있는 AI 예산을 잡아 둔 뒤 기사 제목·요약·주소·매체·발행 시각을 모은다. **AI는 검색하지 않는다** — 모으는 일은 전부 서버가 한다 | 동작 |
| **3** | **선별** | ① 제목·요약으로 본문 확보 우선순위를 정한다 ② 주소를 정리하고 관측을 저장한다 ③ 우선순위 안의 본문을 가져와 정상·유료벽·수집 거부·추출 실패를 기록한다 ④ FULLTEXT끼리 본문 지문을 대조해 같은 글은 **중복군으로 표시하되 매체·기사 행은 남긴다** ⑤ 결정론적 토큰·엔티티로 같은 사건을 이슈로 묶는다 | ②·본문 상태 기록 동작 · ①③의 우선순위·④⑤ P1 |
| **4** | **분석** | 이슈에서 가장 정보가 많은 기사를 골라 먼저 읽는다. 본문을 문장으로 쪼개 번호를 매기고 — **이 번호가 이후 모든 근거의 기준이다** — 요약·핵심 주장·근거 문장 번호·등장 기업·중요도·민감도를 정해진 형식으로 받는다. 형식이 틀리면 한 번만 다시 쓰게 하고, 또 틀리면 실패로 남긴다 | 동작 |
| **5** | **검증** | 주장이 정말 그 문장에서 나왔는지 본다. **아래 검증 5단계가 이 자리다.** 기사의 주장을 한 번에 묶어서 확인하므로 주장 하나마다 AI를 부르지 않는다 | 배치화 P1 |
| **6** | **조사** | 같은 이슈의 기사들을 맞대본다 — 공통으로 말하는 것, 한 곳에만 있는 것, 숫자가 갈리는 것, 빠진 입장. 그러고도 중요한 사건인데 정보가 모자라면 **"B사 반응과 공식 발표를 더 찾아야 한다"고 제안한다.** 검색은 AI가 하지 않는다. 서버가 횟수·예산·중복·허용된 수집원을 검사하고 승인한 것만 실행한다 | P1~P2 |
| **7** | **리포트** | 이슈 단위로 정리한다 — 확인된 사실, 전망, 여러 출처가 함께 말한 것, **엇갈린 보도**, 위험 요소, 더 지켜볼 것, 근거가 모자라 뺀 것. 다 쓰고 나서 한 번 더 본다: 근거 없는 말이 들어갔는지, **근거가 약한 걸 확정처럼 썼는지** | P1~P3 |
| **8** | **기록** | 리포트와 판단 과정을 전부 저장하고, 중요한 이슈는 설정한 조건에 따라 알린다 | 동작 |

**하나로 꿰어 둔다.** 실행 → 이슈 → 기사 → 분석 → 검증 → 추가 조사 → 리포트가 끊기지 않고
이어져야, 리포트의 한 문장에서 원문 문장까지 거슬러 올라갈 수 있다. 무엇을 측정하는지는 §13.

### 검증 5단계

**1단계 · 수집 — 이 기사가 주제와 관련 있는가**
필수 키워드를 전부 포함하고(AND), 선택 키워드를 하나 이상 포함하며(OR), 제외 키워드가 없어야
(NOT) 통과한다. 이 시점엔 본문이 없어 **제목과 요약만** 본다.
> 걸러지는 예: "반도체"가 필수인데 없는 기사

**2단계 · 저장 — 이미 아는 기사인가**
URL을 정규화(추적용 파라미터 제거)해 canonical URL이 같으면 기사 행은 하나로 두고 run/topic 관측을
추가한다. 본문이 확보된 뒤 같은 글은 content group으로 표시하고, 제목 토큰과 결정론적 엔티티로
**같은 사건이면 하나의 이슈로 묶는다.**
> 예: 같은 보도자료를 5개 매체가 받아쓴 것 → 기사·매체 5개 보존, content group 1개, 이슈 1개

**3단계 · 분석 — 원문에 있는 말만 쓰는가**
기사를 문장으로 쪼개고 번호를 매긴다. 요약의 **모든 주장에 근거 문장 번호를 달게 한다.**
번호가 범위를 벗어나면 계약 위반으로 보고 한 번 다시 쓰게 한다.
> 걸러지는 예: 원문에 없는 "3조원 투자"를 지어낸 경우

**4단계 · 검증 — 근거가 정말 그 말을 하는가** ← 핵심

| 단계 | 방법 | LLM |
|---|---|---|
| 4-1 규칙 검사 | 주장의 숫자·날짜·기업명이 근거 문장에 **문자 그대로** 있는가. 부정 표현이 뒤집히지 않았는가. 근거 번호가 원문 범위 안인가 | 안 씀 |
| **4-1-b 강도 검사** | **일이 어디까지 진행됐다고 말하는가.** 검토 → 계획 → 발표 → 승인 → 착수 → 완료를 서로 다른 단계로 보고, 요약이 원문보다 **앞선 단계로 말하면 과장으로 본다** | 안 씀 |
| 4-2 규칙 확정 | 주장이 한 문장 안에 80% 이상 그대로 있으면 LLM 없이 확정 | 안 씀 |
| 4-3 LLM 판정 | 여러 문장에 걸치거나 인과·전망이 섞인 주장만 | 씀 |
| 4-4 사후 재검사 | LLM이 통과시켜도 4-1을 다시 돌린다 | 안 씀 |

> 4-1 예: 주장 "10% 성장" / 근거 "7% 성장" → 숫자 불일치 → 탈락
> 4-1 예: 주장 "계약을 체결했다" / 근거 "계약이 무산됐다" → 부정 반전 → 탈락
> **4-1-b 예: 원문 "투자를 검토 중" / 요약 "투자를 결정했다" → 두 단계 앞섬 → 탈락**
> **4-1-b 예: 원문 "발표했다" / 요약 "승인됐다" → 한 단계 앞섬 → `근거 약함`**
> 4-2 실적: 골든셋 21건 중 **11건이 LLM 없이 끝난다**
> 4-3 결과: `근거 확인` / `근거 약함` / `근거 없음`

**4-1-b가 왜 따로 있나** — 숫자도 기업명도 안 틀렸는데 사실이 아닌 문장이 있다. "검토 중"과
"결정했다"는 글자가 겹치지 않아 4-1이 못 잡고, 문장이 짧아 4-2도 그냥 통과시킨다.
이 한 칸이 없으면 **가장 흔한 종류의 과장이 그대로 리포트에 실린다.**

**5단계 · 리포트 — 실을 자격이 있는가**
근거 없는 항목과 임시 응답(모델 없이 규칙으로만 만든 것)을 제외한다.
제외한 건수를 리포트에 문구로 남긴다: `"근거 부족 3건 제외, 페이월 2건"`

### 우리가 **하지 않는** 것 (이것도 신뢰의 일부다)

- 사실 여부를 **외부 지식으로 판단하지 않는다.** 원문에 있느냐만 본다
- 아직 일어나지 않은 일(전망)은 검증하지 않는다. **전망이라고 표시만** 한다
- **기계가 판정할 수 없는 것은 판정하지 않는다** (`plan-agent-final.md` §15 결정 17)

## 11. 마일스톤

### 11-0. 착수 전 확정: 용어 (`Issue` vs `Event`)

지금 코드에 **`event`가 두 뜻으로 쓰이고 있다.** 이슈를 얹기 전에 정리하지 않으면
세 번째 용어가 생긴다.

| 현재 위치 | 실제 뜻 |
|---|---|
| `AgentTargetType.EVENT` (미사용), `ArticleResDTO.eventId` (항상 null) | **기사 묶음** = 우리가 만들려는 이슈 |
| `agent/app/schemas/report.py` `ReportEventInput{id,title,summaryKo,findingIds}` | **기사 묶음** — 이미 클러스터 형태로 설계돼 있음 |
| `ReportOutput.important_events` | **리포트 항목** — 완전히 다른 개념 |

**확정**

- 기사 묶음 = **`Issue`**. DB `news_issues`, 화면 "이슈"
- 리포트 항목 = `importantEvents` **그대로 둔다** (다른 개념이므로 통합하지 않는다)

> ⚠️ **논의 중에 "Event"로 부르는 안이 다시 나왔다.** 받지 않는다 — `ReportOutput.important_events`가

> F5는 *클러스터링* 임계값 측정에 조건이 걸려 있어서, 그 측정이 끝나는 순간 아무도 의도하지 않은
> 방향으로 결론이 날 뻔했다. 조건을 쓸 때 **"이 측정이 정말 이 항목을 판정하는가"**를 한 번 더 본다.

### 11-8-1. F5 하이브리드 검색 — ✅ **결정됨 (2026-08-31): P3 이월 + 조건 교체**

> **결정** — 기각하지 않는다. **P3 후보로 이월**하고 다시 꺼낼 조건을
> *"§5-2-1 판정표 통과"* → **"이슈가 쌓여 과거 사건을 다시 찾아야 하는 요구가 실제로 나올 때"**로 바꾼다.
> F10-c도 F5에 종속되므로 같이 이월한다. 조건이 차면 그때 M8 임베딩부터 새로 판단한다 —
> 클러스터링 판정(§5-2-1)은 이 결정에 **아무 근거도 주지 않는다.**
>
> **반영처**: `plan-final.md` §4-1(확정 7개 → F5 보류 표시) · §4-4("자르면 안 되는 것" 무효 표시).
> 아래는 왜 이 결정을 했는지의 기록이다.

**이게 "재분류가 필요하다"의 뜻이었다.** 보류 목록의 한 줄이 아니라 **확정 기능 하나의 운명**이 걸려 있었다.

**무슨 일이 있었나**

`plan-final.md` §4-1에서 **F5는 확정 7개 중 하나**였고, §4-4 잘라내기 순서에서
**"자르면 안 되는 것"**으로 못박혀 있었다. 그런데 그 근거가 이거였다:

> *"F5 (F3·F4의 기반)"* · *"임베딩 파이프라인 하나를 깔면 셋이 같이 나온다.
> F5의 임베딩 → F3의 centroid에 재사용 → F4의 근거 유사도 검증에 또 재사용."*

**그 전제가 깨졌다.**

| 기능 | 원래 계획 | 실제 |
|---|---|---|
| F3 이벤트 클러스터링 | F5의 임베딩 centroid 재사용 | ✅ **임베딩 없이** 결정론적 4단계로 완료 (P1-1) |
| F4 근거 추적 | F5의 임베딩 유사도 재사용 | ✅ **임베딩 없이** 문장 인덱스로 완료 (A4 + P0-5) |
| F5 하이브리드 검색 | 둘의 기반 | ❌ **기반이어야 할 대상이 먼저 완성됐다** |

즉 F5를 "자르면 안 되는" 이유는 **사라졌다.** 남은 근거는 §4-1의 두 번째 줄
*"검색 품질, Oracle을 쓰는 명분"* 하나뿐이다.

**딸려 있는 것 — F10-c**

F10(크로스링구얼)도 확정 7개다. F10-a(해외 RSS 시드, M2 ✅) · F10-b(영문→한국어 요약, M4 ✅)는
끝났고 **F10-c(한국어 질의 → 영문 기사 검색)만 M8에 매달려 있다.** F5를 접으면 F10-c도 같이 접힌다.
"한국어로 검색해서 영문 기사가 나온다"는 데모 한 장면이 사라진다는 뜻이다.

**고를 수 있는 것 셋**

| 안 | 내용 | 비용 | 잃는 것 |
|---|---|---|---|
| **(A) 정식 기각** | F5·F10-c를 확정 목록에서 뺀다. Oracle `VECTOR`를 안 쓰는 채로 간다 | 0 | "Oracle 26ai를 왜 골랐나"에 대한 답이 약해진다. M0에서 임베딩 모델을 확정한 작업이 사장된다. **되돌리기 어렵다** |
| **(B) P3로 이월 + 조건 교체** ★ 추천 | 기각도 착수도 아니다. **조건을 바꾼다** — "§5-2-1 판정표 통과"(성립 불가)에서 **"이슈가 쌓여 과거 사건을 다시 찾아야 하는 요구가 실제로 나올 때"**로 | 0 | 없다. 결정을 미루는 대신 **미루는 이유와 다시 꺼낼 조건을 남긴다** |
| **(C) 지금 되살린다** | M8 임베딩 파이프라인부터 다시 깐다 | 2.5~4.5일 + 재색인 운영 부담 | P2가 그만큼 밀린다. **지금 이걸 요구한 사람이 없다** |

**선택: (B).** 이유 셋.

1. **(A)는 되돌리기 비용이 크다.** 확정 7개에서 빼는 건 시연 자리에서 "그건 안 하기로 했습니다"가 되는데,
   F5는 §4-1이 *"핵심"*으로 분류한 항목이라 설명이 길어진다. 반면 (B)는 "조건이 아직 아니다"로 끝난다
2. **(C)를 지금 할 근거가 없다.** 검색 화면 요구가 나온 적이 없고, F5가 떠받치던 F3·F4는 이미 섰다
3. **문제는 F5 자체가 아니라 조건이 잘못 걸려 있던 것이다.** 클러스터링 측정으로 검색 기능의
   운명이 정해지는 구조가 애초에 틀렸다. **조건만 바로잡으면 항목은 살아 있는 채로 남는다**

> ✅ `plan-final.md` §4-1(확정 7개)과 §4-4(잘라내기 순서의 "자르면 안 되는 것")에 **반영 완료.**
> 그 두 줄은 이미 무효가 된 전제 위에 서 있었다.

> **이 결정이 남기는 숙제 하나** — "Oracle 26ai를 왜 골랐나"에 대한 답이 **지금은 `VECTOR`가 아니다.**
> 실제로 쓰고 있는 것은 CLOB `IS JSON` 제약 · 함수 기반 유니크 인덱스 · FULLTEXT 검색 ·
> in-DB ONNX 준비(M0)다. 시연에서 물어보면 **"벡터는 조건이 안 차서 안 켰다"**고
> §5-2-1 판정표를 그대로 보여주는 편이, 안 쓰는 기능을 명분으로 대는 것보다 낫다.

### 12-1. URL 정규화가 기존 데이터를 중복시킨다 (P0-2)

`uq_article_url_hash UNIQUE (url_hash)`(`V4:107`)가 걸려 있는데, 정규화 규칙을 바꾸면
**이미 저장된 기사의 해시와 새로 수집한 같은 기사의 해시가 달라진다.** UNIQUE 위반은 안 나지만
**같은 기사가 NEW로 한 번 더 저장된다.** 조용히 중복이 쌓인다.

두 경로가 있다.

| 경로 | 방법 | 적합 |
|---|---|---|
| **재수집** | `news_articles`와 하위 FK 테이블을 비우고 다시 수집 | **로컬 개발 단계인 지금은 이쪽.** `plan-final.md`가 배포 없는 로컬 전용으로 범위를 잡았고 데이터 가치가 낮다 |
| 백필 | `url_hash` 재계산 → 정규화 후 충돌하는 행 병합 → FK 재지정 | 운영 전환 시 필요. 스크립트를 미리 써두지 않는다 |

**계획서에 명시하지 않으면 반드시 사고가 난다.** 재수집을 택했음을 P0-2 실행 시 기록할 것.

**P0-2 적용 결정 (2026-08-28, #92)** — 현재는 배포 없는 로컬 개발 단계이므로 **재수집**을
선택했다. 기존 `news_articles`와 하위 FK 데이터는 새 정규화 해시와 섞지 않고 로컬 DB를 초기화한
뒤 다시 수집한다. 운영 데이터 백필·충돌 병합 마이그레이션은 만들지 않는다.

### 12-2. 이슈 단위 분석이 `Finding`을 비운다 (P1-1)

`uq_finding_run_article UNIQUE (run_id, article_id)`(`V5:20`) 구조에서 **대표 기사만 분석**하면
멤버 기사에는 `Finding`이 없다.

- `ArticleQueryServiceImpl`이 `analysis: null`을 내려주게 된다.
  FE 타입은 이미 `analysis: ArticleAnalysis | null`(`types.ts:181`)이라 **타입은 안 깨진다** —
  대신 화면에 "분석 없음"이 뜨는 게 문제다
- **대응**: 멤버 기사 상세는 "이 기사는 *○○* 이슈에 속합니다"로 **이슈 대표 분석에 연결**한다
- `ReportEvidencePolicy.eligibleFindings`(`AgentReportOrchestrator.java:235-243`)도 기사 기준에서
  **이슈 기준으로 재작성**해야 한다

### 12-3. `agent_runs` CHECK 제약은 자동으로 안 늘어난다 (P1-7, A9, P2-5)

```sql
CONSTRAINT ck_agent_task CHECK (agent_task IN ('ANALYZE','VERIFY_EVIDENCE','REPORT','EXPLORE'))
CONSTRAINT ck_agent_target_type CHECK (target_type IN ('ARTICLE','FINDING','EVENT','REPORT','RUN'))
```
(`V8__agent_runs.sql:24-25`)

Java `AgentTask` enum에 값을 추가해도 **DB CHECK는 그대로**라 INSERT가 런타임에 터진다.
P1-7은 V29에서 `SELF_CRITIQUE`·`ISSUE`를 **drop 후 recreate**해 반영했다.
A9의 `INSIGHT`는 V32, P2-5의 `INVESTIGATE`는 V33에서 같은 방식으로 확장한다.
V33 CHECK를 재생성할 때는 V32에서 추가한 `INSIGHT`를 빠뜨리지 않는다.
`ck_agent_target_type`에 `EVENT`가 이미 있으나 미사용이므로 `ISSUE`를 함께 넣는다(§11-0).

### 12-4. 프롬프트를 나눠 올리면 골든셋 비용이 3배 (P0)

P0-1·P0-4·P0-10은 한 번에 묶어 `analyze.ko.v3`과 현재 baseline으로 올렸다. 프롬프트 버전을
올릴 때마다 live 24콜과 기준선 재작성이 필요하다는 제약은 남는다. P1-5의 배치 계약·강도 사다리·
`claimType`도 `analyze.ko.v5`로 한 번에 올렸고, P1-0의 주장 라벨로 전후를 한 번만 비교했다.

### 12-5. `maxLength`가 PAID에서만 무력화된다 (P0-1)

`mindlogic_provider.py:15-25`의 `_UNSUPPORTED_STRICT_SCHEMA_KEYS`가 strict 스키마에서
`maxLength`·`maxItems`를 **떼어낸다.** 즉 **Gemini(FREE)는 길이 제약이 걸리고
Mindlogic(PAID)은 안 걸리는 비대칭**이 생긴다.

- Pydantic validator가 최종 방어선이지만, 그건 **위반 시 repair 1회 후 실패**로 끝난다
- 프롬프트에도 글자 수를 명시해 애초에 안 넘게 한다
- **골든셋을 FREE·PAID 양쪽으로 돌려** 비대칭을 잡는다

### 12-6. 클러스터링을 트랜잭션 안에 넣으면 커넥션이 묶인다 (P1-1)

`CollectionResultWriter` 클래스 주석이 못박고 있다 —
*"HTTP와 대기는 `CollectionExecutor`가 트랜잭션 밖에서 끝내고, 이 메서드는 DB 작업만 한다.
짧게 유지해야 커넥션이 외부 I/O 시간만큼 묶이지 않는다."*

클러스터링은 자카드·엔티티 비교라 **계산이 들어간다.**
`IssueClusterer`는 **트랜잭션 밖에서 계산하고, 결과 쓰기만 안으로** 넣는다.

### 12-7. FE 해시 라우팅 북마크가 깨진다 (P1-3)

`App.tsx:8-12`의 `PAGES`에서 `articles`를 빼면 기존 `#/articles` 북마크가 빈 화면이 된다.
**`articles`를 만나면 `reports`로 리다이렉트**하는 분기를 남긴다.

### 12-8. 본문 없는 기사에 지문 중복군을 걸면 서로 다른 기사가 잘못 묶인다 (P1-1)

`ArticleHasher.contentHash`는 **본문이 없으면 제목+요약으로 지문을 만든다.** 주석이 그 이유를
적어 뒀다 — *"null을 두면 비교할 게 없어져 같은 기사를 실행마다 새로 바뀐 것으로 보게 된다."*

이건 **같은 URL의 변경 판정**에는 맞지만, §5-2 1.5단계처럼 **URL이 다른 기사끼리 비교**하는
용도로 쓰면 성격이 달라진다. 제목과 요약만 비슷한 별개 기사가 같은 중복군으로 묶인다. RSS 요약은 매체가
보도자료 첫 문단을 그대로 쓰는 일이 잦아 **실제로 자주 겹친다.**

**대응 — 셋 다 지킨다**
1. 1.5단계는 **`FetchStatus.FULLTEXT`인 기사에만** 적용한다
2. SimHash는 기존 `contentHash` 변경 판정과 분리해 `news_content_groups.simhash`에 둔다
3. 해밍 임계는 **≤ 3**. 넓히고 싶으면 §5-2-1의 골든 클러스터셋으로 재고 나서 넓힌다

기사 행은 삭제하지 않으므로 오분류 시 `content_group_id`를 해제하고 다시 계산할 수 있다. 다만 잘못 묶인
동안에는 대표 외 기사가 분석 투표에서 빠지므로 과병합(§15 리스크 1)을 계속 측정한다.

### 12-9. 교차 비교 결과에는 근거 문장이 없다 (P1-9)

P0-5가 **리포트의 모든 주장을 문장으로 클릭 이동**하게 만들어 놨다
(`ArticleDetailModal.tsx:53-61` 로직 재사용). 그런데 §5-6의 `crossSource`는
**대표 요청에 넣은 멤버 제목·요약에서 나온 관측**이라 붙일 문장 번호가 없다. 본문 저장 여부와 무관하게
그 요청은 멤버 본문을 입력으로 쓰지 않았기 때문이다.

FE가 "모든 주장에 근거가 있다"고 가정하고 있으면 **`conflicts` 항목에서 빈 근거 버튼이 뜨거나
렌더가 깨진다.**

**대응**
- `crossSource` 항목은 **근거 버튼 대신 출처 매체명 + 기사 링크**를 붙인다. 문장 이동이 아니라 기사 이동이다
- 화면 문구도 다르게 — `근거 3` 이 아니라 `조선일보 · 매일경제 2곳` 처럼
- 승격 분석(§5-6)된 기사만 문장 번호가 생기므로, **승격 여부에 따라 같은 항목의 표시가 달라진다**.
  이걸 예외가 아니라 정상 동작으로 설계해 둔다

### 13-2. 골든 클러스터셋이 실수집보다 쉽다 — ✅ **예고가 맞았다 (2026-09-01)**

> **관측된 간격** — 홀드아웃 precision **1.000** vs 실수집 **90% 과병합**(#118).
> 골든셋에는 기자 바이라인·광고 문구·매체 약어가 **없어서** 그 실패 모드가 표본에 아예 없었다.
> 아래 조치 1(말을 정확하게)과 2(`clusters.v2`)는 이제 권고가 아니라 **#118 수정의 전제**다.
> v2 시드 후보는 `docs/p1-2-real-collection-measurement.md`에 적어 뒀다.

`clusters.v1`은 **수동 이슈 50개를 요약형·부분 어휘형·47시간 후속형으로 확장해 200건**을 만든 것이고
(`articlesPerIssue` 4), 모든 기사에 서로 다른 FULLTEXT 원고를 넣었다. 즉 **묶여야 할 것끼리는
확실히 닮았고 안 묶여야 할 것끼리는 확실히 다르다.** 실수집은 그렇지 않다 — 같은 날 같은 기업의
*다른* 사건, 보도자료를 조금씩 고쳐 쓴 기사, 제목만 낚시성인 기사가 섞인다.

**할 일은 둘이고, 둘 다 코드가 아니다.**

| # | 조치 | 언제 | 비고 |
|---|---|---|---|
| 1 | **말을 정확하게 한다** | 지금 | 시연·문서에서 "정확도 100%"라고 하지 않는다. `"손으로 만든 홀드아웃 골든셋 40건에서 오병합 0건"`이 정확한 표현이다. 수치를 낮춰 말하는 게 아니라 **분모를 같이 말하는 것**이다. 물어보면 골든셋 구성 방법을 그대로 설명한다 — 그게 오히려 신뢰를 만든다 |
| 2 | **`clusters.v2`를 실수집에서 뽑는다** | §13-1 실행 직후 | 위 실행의 이슈 결과를 사람이 훑어 **틀리게 묶인 쌍과 놓친 쌍만** 골라 케이스로 만든다. 새로 라벨을 대량 생산하지 않는다 — **v1이 못 잡은 것만 추가**하는 게 목적이다. 목표는 100% 유지가 아니라 **precision이 실제로 어디서 깨지는지 아는 것** |

> ⚠️ **v2를 만들었다고 임계값을 바로 고치지 않는다.** §5-2-1 판정표와 §5-2-2 홀드아웃 절차를
> 그대로 다시 밟는다. 측정 후 기준을 바꾸지 않는 것이 결정 31이다.

> **우선순위 회고** — §13-1을 먼저 실행했고, 결과에서 드러난 #115·#118을 수정한 뒤
> P1-9와 나머지 P1 작업을 완료했다.

★ **아래 두 문단은 P1-0 착수 전 진단이다. 위 표가 이미 해소했으므로 배경으로만 남긴다.** 현재 24개 case에는 `expectedFailures`가 4건 있다.
그중 grounding 3건은 기업명 바꿔치기·숫자 불일치·부정 반전을 의도적으로 넣었고, 나머지 1건은
한국어 요약 실패다. 그러나 `expectedFailures`는 case-level 기대값일 뿐 **어느 claim이 invalid인지,
valid claim을 잘못 떨어뜨렸는지 계산할 라벨·분모가 없다.** 이 상태로 §6-2-1 사다리를 넣으면
`groundedRate` 변화가 과장 검출 때문인지 정상 주장 오탈락 때문인지 구분할 수 없다.

**P1-0에서 확장할 것** — ✅ **다섯 줄 전부 이행됨 (#104)**

- ✅ 기존 expected failure 4건은 회귀 fixture로 그대로 보존한다
- ✅ negative claim은 숫자 불일치·부정 반전·기업명 바꿔치기·**강도 과장**(검토→결정)·원문에 없는 주장,
  각 3건 이상 총 15건 이상 명시 라벨링한다 → `claims.ko.v1.json` **controls 15건**
- ✅ 같은 유형의 valid claim을 positive control로 붙인다 → **15건**
- ✅ `falsePassRate = invalid claim을 grounded로 통과시킨 수 / invalid claim 수` → **0.133**
- ✅ `falseRejectCount = valid positive control을 weak/ungrounded로 내린 수` → **0**

> **기준선이 남긴 숙제** — 통과한 invalid 2건은 둘 다 `modality-*`(강도 과장) 유형이다
> (`modality-expansion-start-invalid`, `modality-center-completion-invalid`).
> **P1-5 강도 사다리가 정확히 이 둘을 잡으라고 있는 것**이므로, P1-5의 성공 판정은
> "`falsePassRate` 하락"이 아니라 **"이 두 id가 잡히고 `falseRejectCount`가 0에서 안 오른다"**로 보면 된다.

**"오병합률"을 따로 적는 이유** — `precision`은 개발 지표라 시연에서 안 통한다.
`1 − precision`을 **"다른 사건을 한 건으로 잘못 묶은 비율"**로 바꿔 부른다.
같은 수를 두 이름으로 계산하지 않고, 표시만 바꾼다.

마지막으로 **실행당 LLM 호출**과 세 커버리지 지표를 함께 본다. run 3891 기준 실행당 호출은
**51회**로 기본 운영 목표 65회 이하를 충족했다. 전체 70개 이슈를 분석하는 부하 시험은 최대 151콜까지 허용한다. 이슈 귀속률이
올랐다는 이유로 LLM 분석률도 100%라고 말하지 않고, 비용·분석 깊이·리포트 반영을 각각 보고한다.

## 14. 기자의 견해

**구현 완료: P1-5(#120).** 표현 강도 사다리와 같은 검증 계약을 바꾸므로 배치화와 함께 넣었고,
같은 이슈에서 P1-8 리포트 최종 재검증까지 완료했다.

**진단**: `report_service.py:86-125`의 `_limit_unsupported_significance`가 `significance`를
자주 `ungrounded`로 판정해 요약문으로 대체한다. 원인은 **기자의 해석·전망을 사실로 검증하려
들기 때문**이다. 스키마에서 분리하면 이 문제와 피드백이 동시에 풀린다.

`analyze.ko.v3` bullet에 `claimType`:

| 값 | 검증 방식 |
|---|---|
| `FACT` | `evidenceSentenceIds` 필수 + `factual_mismatches` 적용 (현재 동작) |
| `FORECAST` | "전망이라고 쓰여 있는가"까지만 |
| `OPINION` | `attributedTo` 필수 (기자 / 애널리스트 / 기업 임원 / 정부 관계자) |

**활용 셋**
1. 화면에서 사실과 견해를 구분 — 단, **참조 계층에 작은 점으로만** (§9)
2. 이슈의 **논조 분포** — 한 사건을 매체들이 낙관/비관 어느 쪽으로 보는지.
   클러스터링이 있어야만 가능한 것이고, 이슈 도입의 부수 효과다
3. 견해를 grounding 검증에서 제외 → `significance`가 요약문으로 대체되는 현재 문제 해소

> `plan-agent-final.md` §13-4의 FACT/IMPLICATION과 같은 방향이되, `IMPLICATION`(에이전트의 추론)과
> `OPINION`(기사에 실린 타인의 견해)은 다르다. **둘 다 필요하고 후자가 먼저다** —
> 원문에 있는 것을 옮기는 쪽이 검증이 쉽고 위험이 낮다.

## 18. 검증 방법

**에이전트**
```bash
cd agent && uv run ruff check . && uv run pytest
```
```bash
cd agent && uv run python -m app.eval --profile replay --compare app/eval/golden/analyze.ko.v6.baseline.json
```
프롬프트 버전을 올리면 live 프로필에서 `--allow-prompt-version-change`와 새 기준선이 필요하다.
(P2-2에서 v6/sensitivity v2로 올렸으므로 현재 replay 기준선은 `analyze.ko.v6.baseline.json`이다.)

**새로 추가할 지표**: 이슈 병합률(기사 수 / 이슈 수) · 요약 길이 분포(P50/P95) ·
검증 호출 절감률(배치화 전후) · 자기 검증 전후 grounded rate ·
**`falsePassRate` / `falseRejectCount`**(negative case 필요) · 리포트 1건당 비용 · 처리 시간

**P1-5는 두 방향을 같이 본다.** 사다리는 통과율을 낮추는 규칙이라 `groundedRate` 하나만 보면
항상 "나빠진 것"으로 읽힌다. `falsePassRate`(내려가야 함)와 `falseRejectCount`(안 올라가야 함)를
**같은 표에 놓고** 판단한다.

**클러스터링 임계값 스윕** (§5-2-2, P1-1 구현 초안 뒤·완료 판정 전)
```bash
cd BE && ./gradlew test --tests '*IssueClustererGoldenExportTest'
cd agent && uv run --group dev python -m app.eval.cluster_sweep \
  --golden ../BE/src/test/resources/golden/clusters.v1.json \
  --java-pairs ../BE/build/reports/clusters/pairs.json
```
Java 테스트가 정규화 feature·pair score를 먼저 내보내고 Python은 그 결과의 precision/recall 곡선과
비교군만 계산한다. P1-1은 균등 자카드 임계 × 시간창을 훑고, P2-1 IDF 완료 뒤 같은 절차로 가중
자카드를 추가 비교한다. **홀드아웃에서 재확인한 값만** `application.yml`에 넣는다. sklearn은
여기서만 쓰이며 Java 클러스터링을 재구현하지 않는다.

**백엔드**
```bash
cd BE && ./gradlew test
```
클러스터링은 통합 테스트로 — 같은 사건의 서로 다른 매체 기사 픽스처가 이슈 1개로 묶이는지,
반박 기사를 추가하면 `DISPUTED`로 전이하는지. `CollectionRunRepositoryIntegrationTests.java` 패턴을 따른다.

**지문 중복군 테스트는 양방향으로 건다** — 같은 본문의 전재 기사는 같은 content group이 되면서
매체 행은 모두 보존되는지, 그리고 **본문 없이 제목·요약만 비슷한 별개 기사는 같은 group이 되지 않는지**
(§12-8). 뒤쪽이 없으면 회귀를 놓친다.

**프론트엔드**
```bash
cd FE && pnpm lint && pnpm build
```

**엔드투엔드**
1. `.claude/launch.json`으로 dev server 기동 후 브라우저 도구로 확인
2. `AGENT_MOCK=true`로 LLM 없이 파이프라인 전체를 먼저 통과 — 클러스터링·점수화는 전부
   결정론적이라 mock으로 검증된다
3. 실제 LLM 검증은 live 프로필로 수동 실행. 실행 전 `GET /api/usage/llm`으로 잔량 확인
4. 시연 시나리오: 같은 사건 기사가 여러 건 들어오는 주제로 수집 → 이슈 1개로 묶이는지 →
   근거 클릭 시 원문 문장으로 이동하는지 → 속보에 후속이 붙으면 알림이 오는지
5. **엇갈린 보도 시나리오**: 같은 사건을 다른 숫자로 쓴 기사 2건을 넣고 → 이슈 1개로 묶이되
   **상충 보도로 표시되는지** → 그중 1건만 승격 분석되는지 (§5-6)
6. **과장 시나리오**: 본문이 "투자를 검토 중"인 기사를 넣고 → 요약에 "결정"이 나오면
   **`근거 없음`으로 강등되고 이유가 화면에 뜨는지** (§6-2-1, §9)
